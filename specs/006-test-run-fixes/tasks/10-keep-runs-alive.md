# 10 — Keep runs alive across navigation

Spec: item 11, points 2–6 (the clickable rail is task 11). The largest task: it touches every run screen.

**The cause (verified when the spec was written, re-verify):** `HunchesApp.goto_stage` calls `switch_screen`, which removes the outgoing screen; Textual cancels a removed widget's workers (`Widget.remove` → `workers.cancel_node`). `App._replace_screen` keeps a screen that is installed (`App.install_screen`) or in another mode's stack. Overlay screens (Projects, Settings, History, …) are pushed on top, so the stage screen below survives; `switch_to` (changing project) deliberately calls `workers.cancel_all()` after a confirm and stays that way (Q6).

**Do**
1. **Verify and pick the mechanism** against Textual 8.2.8 and its docs: installing the outgoing screen while its work runs (`install_screen` / `uninstall_screen`) versus one mode per stage versus another approach. Write down what you verified (including that a suspended screen's `set_interval` timers and workers keep running and that `ScreenResume` fires on return) in the spec under "Verified in task 10". Pick the smallest option: a plain dict on `HunchesApp` (`kept: dict[int, Screen]`) and `if`s, no registry class.
2. **What counts as running**: the stage screens' long operations only: Search (`screens/search.py`), Tuning dev run (`tune.py`), the Test run (`final.py`), the Threshold sample (`threshold.py`) and the Full run (`run.py`), plus an assistant turn on any screen (it belongs to the `ChatPanel` node, not the screen, so look at how `Worker.node` relates to the screen). Give the five run workers a shared group name (`group="run"`) so they can be told apart from chat and status workers; keep `exclusive=True` semantics as they are. Add `HunchesApp.working(screen) -> bool` (any run worker or chat turn alive) and `HunchesApp.running_stages() -> list[int]` (stages whose run worker is alive).
3. **`goto_stage`**: when leaving a screen with `working(...)` true, keep it (not removed); when the target stage has a kept screen that is **still working**, switch back to that same instance; a kept screen that has finished meanwhile is dropped and a fresh screen is built (it reads its results from the project files on mount, so a finished run shows exactly as if the screen had been open). Prune idle kept screens on every `goto_stage`. `switch_to` drops all kept screens (after the existing confirm and `cancel_all`). Make sure only one instance per stage exists and the screen stack does not grow with repeated navigation.
4. **Upstream blocking**: `HunchesApp.upstream_running(stage) -> str | None` returns the name of a running **earlier** stage that the given stage reads from (any earlier stage with a run worker; Brief, Taxonomy, Gold labelling and Browse are not blocked and do not block). Each of the five run screens' start action (and its button, via the existing `check_action`/disabled logic) is disabled while it returns a name, with the reason shown in the screen's existing note line ("Search is running."). A chat turn never blocks anything.
5. **RUNNING mark in the rail**: in `StatusHeader.refresh_rail`, a stage in `running_stages()` gets a mark and the legend (`kinds`/`MARKS` currently hold `↻ stale` and `◐ incomplete`) gets `<glyph> running`. Pick a glyph that does not collide with those two and renders in common monospace fonts (propose `▶`; Chris verifies it in his terminal, record that under "Needs a human"). The tooltip (`StatusHeader.follow`) also lists it with the word RUNNING. The narrow header (under 100 columns) shows a `RUNNING` badge the way 004 shows STALE/INCOMPLETE (read `refresh_cost`). Cost keeps counting as now.
6. `n`/`p`/Redo plan "Go to" all go through `goto_stage`, so they inherit this; the rail click task (11) will too.
